The Problem

Job hunting for analytics & product roles in India means living in four tabs at once.

Naukri surfaces volume, LinkedIn surfaces the freshest postings, Instahyre surfaces startup roles, Internshala surfaces early-career ones — no single portal covers the whole map. So the real workflow looks like this:

Naukri.com — check
LinkedIn — check
Instahyre — check
Internshala — check

4 tabs open. 4 different filter UIs. Same "Product Analyst" search typed out four times. Duplicate listings copy-pasted into a spreadsheet by hand — every single day the search is repeated.

The Job-To-Be-Done
"When I'm actively hunting for a product or data role, I want every relevant, fresh opening across the portals I already trust gathered in one place and dropped into the tracker I already use — so I can spend my limited hunting time applying, not searching."
— Framed using Clayton Christensen's Jobs-to-be-Done model: design for the outcome the person is hiring the product to deliver, not a feature list.

Progressive disclosure

Instead of one dense README, the setup is chunked into four small, sequential steps — each with a single action. Breaking a scary task into small, visibly-finite steps lowers the perceived effort more than the actual time saved.

One-time cost, framed up front

The copy explicitly says "Complete this setup once, and you're done forever." Naming the cost — and capping it — turns a chore into a transaction the user can consciously accept, rather than an open-ended annoyance.

Known trade-off

Running the scraper on the user's own Google account (via Apps Script) means zero hosting cost and no backend to maintain — but it's a real barrier for non-technical job seekers. More on this in "What I'd fix next."

Hick's Law — chunked, not combined

Job Title, Location and Experience are three separate single-select fields instead of one search-everything box. Fewer, simpler decisions at each step beat one big decision with many variables — it keeps time-to-decide low.

System status visibility

Each portal shows its own status pill and method — Ready / Checking / Offline, Database Cache vs. Real-Time Search — before the user commits to a search. People trust a system more when they can see what it's about to do and why one source might be faster or staler than another.

Transparent funnel

Total Found → After Filters → Fresh Today → Added to Sheet reads left-to-right as a visible filtering pipeline. Instead of silently returning "37 results," the product shows its own reasoning — which builds enough trust that a user will let it run again tomorrow, unsupervised.

Feedback loop

Every action (search, filter, push) has a visible, immediate counter-reaction. A search that just says "Ready" with no numbers leaves the user guessing whether anything actually happened.

Recognition over recall

Source and date filters become tappable chips after results load, instead of fields the user has to remember to set before running a fresh, expensive search. Recognizing a familiar option beats recalling one from memory.

Cheap to undo

Filtering re-slices data already on screen — no network round-trip, no re-scraping four sites. It reframes "narrow this down" as instant and reversible, which encourages exploration instead of caution.

Meet users in their existing tool

The JTBD isn't "give me a beautiful new dashboard" — job seekers already track applications in a spreadsheet. Job Hunterz N18 writes straight into that sheet instead of asking Aditi to adopt a second system and reconcile two lists.

Honest empty state

Before any search runs, the table reads: "Ready to search. Click Search All Job Portals above. Results will appear here automatically." — a plain instruction instead of a blank void, so a first-time user is never stuck wondering what to do next.

What I'd Fix Next

The honest part of the case study.

A few decisions traded mainstream usability for zero hosting cost and fast shipping. Here's where I'd spend the next iteration.

The Apps Script setup is a real wall

Copy-pasting code into script.google.com and deploying a web app is second nature for a developer, not for most job seekers.

Next iterationOffer a one-click hosted backend (even a shared free tier) as the default path, and keep "bring your own Apps Script" as the power-user option.

"Local Server Offline" leaks the system model

Asking a user to double-click start.bat surfaces an implementation detail — a local scraper process — that they shouldn't need to know exists.

Next iterationRewrite the warning in plain outcome language ("Live results are paused — restart search") and attempt auto-recovery before ever mentioning a file.

Fixed 11-city location list

No "Remote" option and no freeform city entry means the tool quietly excludes valid searches outside the preset list.

Next iterationAdd a searchable freeform location field with the current 11 cities as quick-pick shortcuts.

No saved searches or alerts

Aditi has to remember to come back and manually re-run the same search every day to catch new postings.

Next iterationLet a search be saved and scheduled, with new matches surfaced as a daily digest instead of a manual re-hunt.

Outcomes & Learnings

What building this taught me as a PM.

  • Naming a cost is better than hiding one. The setup wizard doesn't pretend the Apps Script step is easy — it says "one-time" and gives an escape hatch, which earns more trust than a vague "Get Started" would.
  • Visible system state turns a black box into a tool people trust daily. The portal status pills and the found → filtered → fresh funnel are what make someone comfortable re-running an automated search unsupervised.
  • Design for the existing habit, not a new one. Writing results straight into the spreadsheet users already track applications in removed an entire adoption step the product didn't need to ask for.
  • The friction I chose to keep is still a decision worth defending — or fixing. Writing the "What I'd fix next" section made the real trade-offs (cost vs. accessibility) explicit instead of invisible.
